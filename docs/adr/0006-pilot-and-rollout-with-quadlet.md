# 0006. Pilot and rollout with Podman Quadlet, health checks and automatic rollback

- Status: Accepted
- Date: 2026-11-15
- Issue: #15
- Deciders: product owner, conductor
- ArchiMate elements: id-bus-proc-deploy, id-tech-node-pilot, id-tech-node-prod, id-tech-sw-podman

## Context and problem
A released image (ADR 0005) must reach users safely: first one pilot host, then production
after a human decision, never leaving a host broken. There are no servers yet, and GitHub's
cloud runners cannot reach hosts on a desktop.

## Decision drivers
- Run exactly the accepted bytes (digest), with automatic recovery when a release is bad.
- Human approval before production (gate 3), and an audit trail.
- The same scripts for simulated hosts today and real VMs later.

## Decision
- **Runtime**: each host runs the image as a systemd user service generated by **Podman Quadlet**
  (`deploy/rust-factory.container.in`): restart on failure, `Notify=healthy` (the unit is "active"
  only after the image's own health check passes), unhealthy containers are killed and restarted.
- **Hosts as data**: `deploy/hosts/<env>.txt` with a transport per host: `local` (simulated host
  on this machine, own port) or `ssh:user@host` (real VM). Only the transport differs.
- **Deploy** (`scripts/deploy.sh`, `just deploy`): resolve version → digest; per host write the
  unit, blocking restart, then healthy = *container runs the expected image* AND *unit active* AND
  `/health` answers, within 30 s; on failure roll back to the previous image and verify it.
  Production is rolled host by host and stops at the first failure.
- **Promote** (`just promote X.Y.Z`): only a version the pilot is running healthily. This is
  human gate 3: agents never run it.
- **Audit**: every deploy is recorded as a GitHub Deployment (environments `pilot`,
  `production`, success/failure); board items in the release move to **Piloted** / **Released**.

## Consequences
- Good: a bad release on the pilot rolls itself back (drill: crashing image → rolled back, exit 1,
  pilot kept serving); a bad production rollout stops at the first host.
- Bad: deployments run from the developer machine, not from GitHub Actions. The audit trail is
  in GitHub, but the approval is "the human ran promote", not an Environment reviewer. With real
  VMs, the same steps can move into a workflow with Environment protection.
- Bad: the SSH transport is untested until the first VM exists.

## What the drills found (and why they matter)
1. **`HealthCmd=/app healthcheck` in the Quadlet unit** is passed to Podman as a *shell* command;
   the distroless image has no shell, so the check could never pass → restart loop. Fixed by using
   the image's exec-form HEALTHCHECK.
2. **The first deploy "succeeded" during that loop**: the app answered `/health` between restarts.
   Fixed: healthy also requires systemd to report the unit active.
3. **A non-blocking restart let the old container answer the health check**: the broken image
   "deployed successfully" and the pilot went down. Fixed: blocking restart, and the check verifies
   the running container's image. Re-run drill: rolled back automatically.
Lesson: deployment safety code must itself be tested by deliberately failing deploys.
